# StudyBridge 탐구 일지 양식

이 문서는 기록 양식과 가상 작성 예시다. 실제 실험 결과·완료 실적으로 제출하기 전에 수행한 날짜, 입력값, 결과, 증거로 바꾼다.

## 1. 회차별 기록 양식

- 날짜·회차:
- 이번 목표:
- 탐구 질문: 무엇을 확인하려고 했는가?
- 예상 또는 가설: 왜 그렇게 예상했는가?
- 작업 내용: 어떤 화면·코드·테이블·설정을 바꾸었는가?
- 검사 환경: 로컬 / Preview / Production, 데모 / 실제 테스트 DB
- 검사 방법: 사용 계정의 역할, 입력값, 클릭 순서, 예상 결과
- 실제 관찰: 성공·실패·미확인으로 구분하고 실제 결과를 기록
- 문제 원인과 근거: 로그, 코드, DB 상태를 바탕으로 설명
- 수정 내용과 재검사:
- 배운 점:
- 남은 문제·다음 계획:
- 증거: Issue·PR 번호, 커밋, 비밀값을 가린 로그·화면, 배포 주소

## 2. 개발 단계별 탐구 질문

| 단계 | 탐구 질문 | 관찰할 자료 |
|---|---|---|
| 화면 제작 | 입력한 조건이 다음 화면까지 유지되는가? | 요청 작성 전후 화면과 상태 |
| 코드 관리 | 기능별 변경 기록이 오류 원인 추적에 도움이 되는가? | 커밋·PR 변경 내용 |
| DB 설계 | 신청과 최종 연결을 다른 표로 나누면 무엇이 명확해지는가? | 한 요청에 여러 신청·하나의 연결 |
| 로그인 | 메일 인증 전후에 저장 권한이 어떻게 달라지는가? | 로그인 상태, 프로필 생성 결과 |
| 추천 계산 | 시간 필터가 없으면 어떤 부적절한 추천이 생기는가? | 같은 입력에 필터 적용 전후 결과 |
| 접근 권한 | 화면 버튼을 숨기는 것만으로 다른 사람의 수정을 막을 수 있는가? | 제삼자 테스트 계정의 실제 거절 결과 |
| 동시 수락 | 마지막 한 자리에 두 신청을 동시에 수락하면 어떻게 되는가? | 승인 결과와 최종 활동 인원 |
| 배포 설정 | 로컬 환경 변수가 배포 사이트에 자동 적용되는가? | 환경별 설정 이름·연결 대상·로그 |
| 최종 평가 | 추천이 실제 신청과 만남으로 이어지는가? | 신청·수락·첫 회차 진행 결과 |

권한·동시 수락 실험은 본인이 관리하는 테스트 계정과 테스트 DB에서 진행한다.

## 3. 가상 작성 예시: 환경 변수와 데모 모드

아래 서술은 실제로 수행했다는 주장이 아닌 작성 방식의 예시다.

**목표:** 배포 주소에서도 도움 요청이 실제 DB에 저장되는지 확인한다.

**탐구 질문:** 화면이 정상적으로 열리면 DB 연결도 성공했다고 판단할 수 있을까?

**가설:** Vercel에 화면은 배포되어도 DB 연결 설정이 빠져 있으면 실제 저장은 되지 않을 수 있다.

**검사 계획:** Preview를 데모 모드로 실행한 경우와 실제 테스트 DB에 연결한 경우를 비교한다. 동일한 요청을 작성하고 새로고침·로그아웃·재로그인 후 다시 조회한다. DB의 해당 요청도 확인한다.

| 조건 | 예상 결과 | 실제 결과 |
|---|---|---|
| 데모 모드 | 화면 예시는 보이지만 실제 DB 기록은 생성되지 않음 | 검사 후 기록 |
| 테스트 DB URL·공개 키 + 데모 false | 요청이 저장되고 다시 조회됨 | 검사 후 기록 |
| 다른 학생으로 로그인 | 공개 범위에 따라 조회되고, 다른 사람 요청은 수정할 수 없음 | 검사 후 기록 |

**분석 방법:** Vercel 배포 성공 여부, 환경 변수, 실제 DB 저장 여부를 따로 확인한다. 현재 프로젝트의 데모 데이터 직접 조회도 확인하여, 환경 변수 누락과 조회 코드 미완성을 구분한다.

**기록 예시 문장:** 실제 검사 후에만 “환경 변수 설정과 실제 DB 조회 코드를 함께 수정한 뒤, 새로고침과 재로그인 후에도 요청이 유지되는 것을 확인했다”라고 작성한다.

## 4. 가상 작성 예시: 마지막 자리의 동시 수락

**탐구 질문:** 남은 정원이 1명일 때 두 신청을 거의 동시에 수락하면 정원이 초과될까?

**가설:** 두 처리가 각각 남은 정원을 먼저 읽으면 모두 자리가 있다고 판단할 수 있다.

**검사 계획:** 테스트 멘토의 정원을 1명으로 설정하고 서로 다른 멘티의 요청 두 개를 준비한다. 동시에 수락을 시도한 뒤 신청 상태와 최종 연결 수를 확인한다. 같은 멘토의 수락 처리를 순서대로 보호하도록 보완한 후 같은 실험을 반복한다.

**예상 결과:** 한 신청만 수락되고 다른 신청에는 정원이 찼다는 결과가 전달된다. 최종 활동 인원은 1명을 넘지 않는다.

**실제 결과·근거:** 검사 후 기입한다. 현재 로컬 코드 검토에서 보완 필요성을 찾았다는 사실과, 실행 실험으로 결과를 확인했다는 사실을 구분한다.

## 5. 결과 보고 시 사용할 표현

| 상황 | 적절한 표현 |
|---|---|
| 설계만 마침 | “테이블 관계와 권한 규칙을 설계했다.” |
| 코드가 있음 | “해당 기능의 코드를 작성했다.” |
| 데모에서 검사함 | “데모 데이터로 화면 흐름을 확인했다.” |
| 실제 테스트 DB에서 검사함 | “테스트 DB에 저장한 뒤 재조회되는 것을 확인했다.” |
| 운영에 배포하고 확인함 | “운영 주소에서 해당 기능을 검사했고, 결과를 기록했다.” |
| 아직 확인하지 못함 | “해당 조건의 검사는 남아 있으며 다음 회차에 확인할 예정이다.” |

비밀키·비밀번호·학생 이메일을 화면 캡처나 일지에 넣지 않는다. 환경 변수는 이름과 용도만 적고 실제 비밀값은 기록하지 않는다.
